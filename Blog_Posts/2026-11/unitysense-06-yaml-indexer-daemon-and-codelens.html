Rider로 Unity 스크립트를 읽을 때 편리한 기능 중 하나는 클래스와 필드, 메서드 상단에 뜨는 에셋 사용처(Asset Usages)와 인스펙터 직렬화 값 표시입니다. 이 스크립트가 어느 씬이나 프리팹에 붙어 있는지, 버튼의 UnityEvent에 어떤 메서드가 연결되어 있는지 코드 에디터를 벗어나지 않고 바로 파악할 수 있기 때문입니다.

하지만 Unity의 .unity 씬과 .prefab 파일은 크기가 수십 MB에 달할 수 있고 프로젝트당 수천 개가 쌓이기도 합니다. 이를 VS Code Extension Host(단일 스레드 Node.js)에서 파싱하면 에디터가 멈추기 때문에, 별도의 .NET 8 백그라운드 데몬(UnityBrain.Daemon)으로 분리해 구현했습니다. 이번 글에서는 무할당 스트리밍 YAML 파서, UBIX 바이너리 캐시, 그리고 JSON-RPC 통신 안정화 과정을 살펴보겠습니다.

1. DOM 파서 대신 1-Pass 스트리밍 상태 머신을 선택한 이유

YamlDotNet 같은 범용 YAML DOM 파서는 파일 전체를 메모리 트리로 올리기 때문에 대용량 씬 파일 수백 개를 동시에 스캔할 때 GC 부담과 메모리 점유가 급격히 커집니다. UnityYamlStreamParser.cs는 필요한 정보만 뽑아내는 StreamReader + ReadOnlySpan<char> 기반 1-Pass 라인 상태 머신으로 작성했습니다.

flowchart LR
    Assets[".unity / .prefab / .asset"] -->|"1-Pass ReadOnlySpan 스캔"| Parser["UnityYamlStreamParser"]
    Meta[".cs.meta / .asset.meta"] -->|"병렬 GUID 매핑"| GuidMap["MetaGuidMap"]
    GuidMap --> Parser
    Parser -->|"증분 직렬화"| Cache["UBIX 바이너리 캐시 (asset-index.bin)"]
    Cache -->|"Content-Length JSON-RPC 2.0"| Client["UnityDaemonClient (VS Code)"]
    Client -->|"사용처 / 인스펙터 값 / UnityEvent"| Lens["C# CodeLens & QuickPick"]

파서는 --- !u!<classID> &<fileID> 문서 경계를 만날 때마다 컨텍스트를 전환하며 네 가지 핵심 블록만 추출합니다.

  • !u!1 (GameObject) 및 !u!4/!u!224 (Transform/RectTransform): 오브젝트 이름과 부모-자식 연결을 수집한 뒤, 1-Pass 종료 후 O(N) 부모 역추적으로 Canvas/HUD/PlayerHealthBar 같은 계층 경로를 조립합니다.
  • !u!114 (MonoBehaviour): m_Script의 GUID를 MetaGuidMap과 대조해 프로젝트 스크립트인 경우 사용자 직렬화 필드 값과 m_PersistentCalls의 UnityEvent 콜백 메서드(m_MethodName)를 수집합니다.
  • !u!1001 (PrefabInstance): Nested Prefab과 Prefab Variant의 m_Modifications에서 중첩 propertyPath 오버라이드 값을 추출합니다.

2. UBIX 증분 캐시와 JSON-RPC 프로토콜 안정화

매번 워크스페이스를 열 때마다 전체 에셋을 다시 파싱하지 않도록 Library/UnityBrainCache/asset-index.bin에 "UBIX" 헤더와 파일별 (LastWriteTicks, Length) 매니페스트, 인덱스 레코드를 바이너리로 저장합니다. 재실행 시에는 변경되거나 새로 추가된 파일만 재파싱하고 삭제된 항목만 제거합니다. 합성 .prefab/.unity 1,000개 대상 자동화 벤치마크 테스트에서는 풀 인덱싱 500ms 미만, 단일 파일 수정 후 웜 스타트 150ms 미만 조건을 통과시켰습니다.

Extension Host(UnityDaemonClient)와 데몬(RpcServer.cs) 간 stdio 파이프 통신을 다듬는 과정에서는 실전 프로토콜 이슈 세 가지를 수정했습니다.

  1. 파이프라인 연속 프레임 오버리드 제거 (v1.1.2): RpcServer.ReadFrameAsync가 버퍼 단위로 헤더를 읽으면 연속 요청된 다음 프레임의 바이트까지 미리 읽어 프레이밍이 깨졌습니다. 헤더를 1바이트 단위로 읽어 \r\n\r\n 경계를 정확히 끊은 뒤 Content-Length만큼 본문을 읽도록 고쳤습니다.
  2. 잘못된 JSON 입력 시 표준 에러 응답 (v1.1.4): 손상된 JSON 요청이 들어왔을 때 응답 없이 타임아웃까지 대기하던 문제를 JSON-RPC 표준 -32700 Parse error 즉시 반환으로 수정했습니다.
  3. 타임아웃 분리와 서킷 브레이커 (v1.1.2, v1.1.4): 일반 조회 타임아웃은 15초로 두고 전체 재인덱싱(index/rebuild)은 60초로 분리했으며, 프로세스 비정상 종료 시 5초 쿨다운·서킷 브레이커와 bounded stderr 드레인을 적용했습니다.

배포 호환성 측면에서는 UseNet8Release=true와 rollForward: Major 설정을 적용해, .NET 8, .NET 9, .NET 10 런타임이 설치된 어느 PC에서도 동일한 UnityBrain.Daemon.dll이 실행되도록 구성했습니다.

⚠️ 주의: 합성 1,000개 에셋 벤치마크와 JSON-RPC 단위 테스트는 통과했으나, 실제 거대한 상용 Unity 프로젝트에서 초기 인덱싱이 어느 정도 소요되는지와 Nested Prefab·Prefab Variant 오버라이드 값이 복잡한 실무 계층에서도 정확히 표시되는지는 실제 사용 사례에서 추가 검증이 필요한 상태입니다.

마무리하며

무거운 YAML 스캔을 .NET 8 독립 프로세스와 ReadOnlySpan<char> 스트리밍 파서로 격리하면서 VS Code의 UI 반응성을 해치지 않는 구조를 만들었습니다. 이제 남은 과제는 합성 테스트가 아닌 실제 대형 프로젝트에 올려 초기 인덱싱 시간과 Prefab Variant 표시 정확도를 확인하고 다듬는 일입니다.

혹시 대규모 Unity 프로젝트에서 씬·프리팹 YAML 역참조 검색을 빠르게 처리하기 위해 별도로 구축해 보신 툴이나 캐싱 전략이 있으신가요? 댓글로 경험을 나눠주시면 감사하겠습니다. 다음 글에서는 .meta 동기화, .asmdef 순환 참조 진단, UI Toolkit, 그리고 Unity Editor UDP 연동을 다루겠습니다.
