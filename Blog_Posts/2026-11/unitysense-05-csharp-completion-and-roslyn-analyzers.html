셰이더 영역의 공백을 메운 뒤에는 C# 스크립트 편집 경험을 끌어올릴 차례였습니다. Microsoft 공식 C#/Unity 확장도 기본적인 C# IntelliSense와 UNT0001~UNT0038 진단을 제공하지만, Rider에서 자주 쓰던 문자열 컨텍스트 자동완성(Tag, Layer, Build Scene, Shader Property 등), 헬퍼 메서드를 거친 간접 성능 경고, 그리고 Ctrl+. 한 번으로 Awake() 캐싱 코드를 만들어 주는 Quick-Fix는 빠져 있었습니다.

이번 글에서는 ProjectSettingsWatcher 기반 도메인 자동완성, Unity의 .csproj 덮어쓰기를 회피하는 Directory.Build.props 비침습 MSBuild 주입, 그리고 UB1xxx~UB4xxx Roslyn 정적 분석기와 CodeFix 구현 과정을 정리합니다.

1. 프로젝트 설정 감시, 도메인 자동완성과 Hover/F12 분리

Unity의 ProjectSettings/TagManager.asset, InputManager.asset, EditorBuildSettings.asset, 그리고 .controller 파일은 !u! 태그를 포함한 비표준 YAML 포맷입니다. 범용 YAML 파서에 그대로 넣으면 오류가 발생하므로, 전용 경량 파서(ProjectSettingsWatcher)가 300ms 디바운스로 이 파일들을 감시해 Library/UnityBrainCache/project-settings.json으로 동기화하도록 구성했습니다.

UnityStringCompletionProvider는 CompareTag(", LayerMask.GetMask(", Input.GetAxis(", SceneManager.LoadScene(", Material.SetFloat(", Animator.SetTrigger(", Resources.Load(", .Q<T>(" 같은 특정 API 문자열 리터럴 내부일 때만 후보를 반환합니다. 일반 C# 코드 위치에서는 아무것도 반환하지 않아 C# Dev Kit의 기본 자동완성과 충돌하지 않습니다.

또한 C# 문자열에서 Ctrl+Hover와 F12 동작을 명확히 분리했습니다. provideDefinition이 Hover 시점에 UDP 패킷 전송이나 토스트 알림 같은 부작용을 일으키지 않도록 순수 vscode.Location만 반환하게 하고, F12(unitySense.csharpGoToDefinition) 실행 시에만 실행 중인 Unity Editor UDP 이동과 로컬 파일 폴백을 처리합니다.

2. Directory.Build.props 비침습 주입과 UB1~UB4 Roslyn 분석기

Unity Editor는 스크립트를 추가하거나 수정할 때마다 프로젝트의 .csproj 파일을 재생성해 덮어씁니다. 따라서 .csproj를 직접 수정해 Roslyn 분석기를 등록하면 곧바로 초기화됩니다. 이를 피하기 위해 프로젝트 루트의 Directory.Build.props에서 <!-- UnityBrain:Begin -->과 <!-- UnityBrain:End --> 마커 사이만 idempotent하게 관리하는 MsbuildAnalyzerInjector를 작성했습니다. 경로 내 MSBuild 특수문자(%, ', ;, $)는 %25, %27, %3B, %24로 선행 이스케이프 처리합니다.

진단 대역 분석 및 CodeFix 내용
UB1001 / UB1002 Update·FixedUpdate·LateUpdate 등 성능 민감 루트에서 클래스 내 콜그래프(BFS)를 추적해 간접 호출된 GetComponent<T>(), Camera.main, FindObjectOfType 탐지 및 Awake() 자동 캐싱 Quick-Fix/CodeFix 제공
UB1003 Material.Set*, Animator.Set* 문자열 인자를 static readonly int 정적 필드(Shader.PropertyToID / Animator.StringToHash)로 자동 추출
UB2001 ~ UB2004 [BurstCompile] 컨텍스트 내 관리형 참조 타입, Boxing, 문자열 보간·연결, 예외(try/catch/throw) 정적 검증 ([BurstDiscard] 예외 허용)
UB3001 ~ UB3003 AdditionalFiles의 project-settings.json을 참조해 존재하지 않는 Invoke/StartCoroutine 메서드명, Tag/Layer, Build Scene 경고
UB4001 & 경고 억제 직렬화 필드 이름 변경 시 [FormerlySerializedAs] 자동 부착 및 [SerializeField] 대상 CS0649/CS0169/IDE0051 경고 억제(DiagnosticSuppressor)

3. SequentialFixAllProvider와 netstandard2.0 호환성 해결

Roslyn 분석기와 Extension Quick-Fix를 실제 코드 패턴에 적용하면서 세 가지 중요한 버그를 해결했습니다.

  1. 다중 Fix All 시 중복 Awake() 충돌 (v1.1.6): 한 클래스 안에 여러 UB1001/UB1002/UB1003 경고가 있을 때 기본 병렬 FixAllProvider를 돌리면 각 수정본이 서로의 Awake() 생성 여부를 몰라 메서드가 중복 생성되었습니다. SequentialFixAllProvider를 도입해 순차 적용하도록 바꾸고, 다른 partial class 파일에 이미 Awake()가 있는 경우에도 Solution 단위 CodeAction으로 해당 메서드에 초기화 구문을 주입해 런타임 NullReferenceException을 막았습니다.
  2. C# 11 문자열 및 식 본문 Awake() => ...; 처리 (v1.1.6): C# 11 raw string("""..."""), 중첩 보간식, 주석 안의 Camera.main 오탐과 Awake() => Init(); 식 본문 메서드가 Quick-Fix를 깨뜨리는 문제를 maskCSharpCommentsAndStrings 보강과 식 본문 블록 자동 변환으로 해결했습니다.
  3. 오프라인 .NET 10 SDK vs netstandard2.0 프로파일 이중화 (v1.1.1, v1.1.4): 로컬 PC는 오프라인 .NET 10 SDK 환경이지만 C# Dev Kit의 Roslyn 호스트 표준은 netstandard2.0입니다. UseNuGetNetStandard=true 릴리스 프로파일(Microsoft.CodeAnalysis.CSharp.Workspaces 4.3.1)을 분리하고, netstandard2.0 비호환 .Contains 호출 3건과 SimpleJson UTF-8 BOM 처리를 수정했습니다.
⚠️ 주의: [SerializeField] 필드에 대한 CS0649/CS0169/IDE0051 경고 억제(DiagnosticSuppressor)는 정상 동작을 확인했고 기본 체감 속도도 무난했습니다. 다만 스크립트 수가 많은 복잡한 실무 프로젝트에 적용했을 때의 장기적인 부하와 안정성은 앞으로 실제 프로젝트에서 사용하며 확인해야 할 영역입니다.

마무리하며

Directory.Build.props를 통한 비침습 주입 덕분에 Unity가 .csproj를 수시로 재생성해도 Roslyn 분석기와 AdditionalFiles 연결이 끊어지지 않게 되었습니다. 특히 Camera.main과 GetComponent<T>()의 Awake() 자동 캐싱, 그리고 [SerializeField] 미사용 경고 억제는 C# 편집 시 체감 빈도가 높은 부분입니다.

혹시 Unity C# 프로젝트에서 Directory.Build.props를 활용해 사내 커스텀 Roslyn 규칙이나 코드 스타일을 적용해 보신 경험이 있다면 댓글로 공유해 주시면 감사하겠습니다. 다음 글에서는 씬과 프리팹 YAML을 백그라운드에서 스트리밍 인덱싱하는 .NET 8 데몬과 C# CodeLens 구현을 다루겠습니다.
