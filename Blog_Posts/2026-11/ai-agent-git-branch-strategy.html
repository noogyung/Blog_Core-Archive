개인 프로젝트를 진행하다 보면 다수 인원의 협업을 전제로 설계된 Git Flow는 절차가 번거롭고, 반대로 단일 브랜치 위주의 단순한 구조는 버전별 배포 이력을 보존하거나 실험 코드를 격리하는 데 한계가 있습니다. 특히 최근처럼 1인 개발 환경에서 Antigravity나 Codex 같은 AI 코딩 에이전트에게 기능 구현과 R&D를 위임하는 비중이 높아지면서, 기존의 느슨한 브랜치 운영 방식에서 예상치 못한 히스토리 오염 문제가 드러났습니다.

최근 크롬 확장 프로그램 프로젝트인 WebTranslator의 차기 버전을 개발하던 중, 배포용 브랜치와 개발용 브랜치의 경계가 무너지고 자동화 스크립트가 작업 브랜치를 강제로 고정해버리는 문제를 뒤늦게 발견했습니다. 이번 글에서는 WebTranslator에서 실제로 겪은 브랜치 관리상의 문제 원인을 짚어보고, 이를 해결하기 위해 평소 개인 작업 방식에 맞춰 재정립한 개인 개발용 3계층 Git 브랜치 관리 전략을 정리해보고자 합니다.

💡 안내: 이 글에서 다루는 브랜치 구조와 스크립트 규칙은 모든 개발 팀이나 프로젝트에 일괄 적용되는 범용 표준이 아닙니다. 혼자 개발을 진행하면서 AI 에이전트에게 단위 작업을 지시하고, 스토어나 패키지 형태로 개별 버전별 배포 히스토리를 남겨야 하는 개인 개발 환경에 맞추어 설계한 기준입니다.

1. WebTranslator에서 확인된 3가지 브랜치 관리 문제

WebTranslator v1.0.0을 Chrome Web Store에 정식 배포한 이후, v2.0.0의 핵심 기능인 온디바이스 및 하이브리드 이미지 번역 파이프라인을 개발하는 과정에서 크게 세 가지 구조적 문제가 발생했습니다.

1.1 배포 스냅샷 태그 누락과 main 브랜치 오염

첫 번째 문제는 정식 배포 버전이 위치해야 할 main 브랜치에 차기 버전의 미완성 코드가 섞여 들어간 점입니다. 로컬 커밋 로그를 역추적해보니 실제 Chrome Web Store에 v1.0.0으로 패키징하여 배포한 시점은 0237429 커밋이었습니다. 그러나 당시 별도의 Git Tag(v1.0.0)를 생성해두지 않았습니다.

더 큰 문제는 그 직후에 발생한 1b68205 커밋이었습니다. 해당 커밋의 메시지는 문서 정리와 후원 링크 반영(docs: README 및 프로젝트 명세서 추가, 폴더 구조 정리 및 후원 정책 반영)이었지만, 실제 변경된 파일 트리를 확인해보니 워킹 디렉토리에서 작업 중이던 v2.0.0 이미지 번역 모듈(src/content/image/*, src/api/imageTranslate.js)과 manifest.json의 버전 변경(1.0.0 → 2.0.0)까지 총 65개 파일이 한꺼번에 스테이징되어 main 브랜치에 커밋되어 있었습니다.

⚠️ 증상 및 원인 분석: 문서 수정 작업과 차기 버전 기능 개발이 동일한 워킹 트리에서 분리되지 않은 상태로 진행되었고, main 브랜치 직접 커밋을 막는 가드레일 없이 전체 스테이징(git add)이 실행되면서 배포 기준선이 오염되었습니다.

1.2 버전 문자열 기반 강제 브랜치 라우팅의 역효과

두 번째 문제는 프로젝트 내 에이전트 규칙 파일인 .agents/AGENTS.md와 자동 동기화 스크립트인 scripts/git-sync.ps1의 설계 결함이었습니다. 당시에는 버전 관리를 자동화하려는 의도로 manifest.json의 버전 값을 읽어 브랜치를 자동으로 전환하는 로직을 작성해두었습니다.

# 기존 scripts/git-sync.ps1 내부의 문제 구간
$manifest = Get-Content $manifestPath -Raw | ConvertFrom-Json
$version = $manifest.version

$targetBranch = "main"
if ($version -notmatch "^1\.0\.") {
    $majorMinor = ($version -split '\.')[0..1] -join '.'
    $targetBranch = "v$majorMinor-dev"
}

if ($currentBranch -ne $targetBranch) {
    git checkout $targetBranch
}

위 로직은 manifest.json의 버전이 2.0.0인 동안에는 현재 어떤 브랜치에 있든 무조건 v2.0-dev로 강제 체크아웃한 뒤 git add -A와 원격 푸시를 수행합니다. 즉, 새로운 실험이나 기능을 분리하기 위해 별도 브랜치를 생성하더라도 동기화 스크립트를 실행하는 순간 다시 v2.0-dev로 되돌아가 버리는 구조적 제약이 발생했습니다.

1.3 단일 개발 브랜치(v2.0-dev) 내 R&D 시행착오 누적

세 번째 문제는 AI 에이전트를 통한 수많은 R&D 실험이 격리 없이 v2.0-dev 단일 브랜치에 직렬로 쌓인 점입니다. 이미지 번역 파이프라인을 구축하면서 Tesseract.js 검증, PaddleOCR 전환, ONNX Runtime Web 기반 PP-OCRv6 도입, 스프라이트 시트(Sprite Sheet) 병합 호출, 그리고 에이전트가 잘못 수정한 코드를 되돌리는 롤백 커밋까지 총 48개의 커밋이 한 줄기로 누적되었습니다.

* f56a48e feat(premium): add annotated/crop synthesis modes and short-edge 1024px compression
* 0e3fa4e revert(image): remove diagnostic page and related code
* c6232d0 feat(image): add staged image translation diagnostics and replay
* 506c416 revert(image): roll back all Codex changes
* 05215ab fix(image): rollback Codex changes and separate OCR from synthesis
* 0b74cb6 Revert "feat(imageService): 2-pass A-plan - Gemini detect + OpenAI translate"
* 3c61cc3 feat(imageService): 2-pass A-plan - Gemini detect + OpenAI translate

실험적 시도를 별도 샌드박스 브랜치로 분리하지 않고 통합 브랜치에서 바로 커밋하다 보니, 실패한 접근법을 걷어낼 때마다 revert 커밋이 연쇄적으로 발생하여 특정 시점의 안정적인 코드로 복귀하거나 변경 이력을 파악하기가 어려워졌습니다.

2. 개인 개발용 3계층 브랜치 아키텍처 설계

앞서 살펴본 문제를 해결하기 위해, 혼자 작업하면서 AI 에이전트를 적극적으로 활용하고 버전별 배포 히스토리를 명확히 남겨야 하는 조건에 맞춰 3계층 브랜치 + Git Tag 구조를 수립했습니다.

flowchart TD
    subgraph Tier3["Tier 3: AI 작업 및 실험 격리선"]
        Exp["exp/* (R&D 실험 샌드박스)<br/>자유로운 중간 커밋 허용"]
        Feat["feat/* & fix/* (단위 기능/수정)<br/>단일 목적 구현"]
    end

    subgraph Tier2["Tier 2: 버전 통합선"]
        Dev["v{Major}.{Minor}-dev (예: v2.0-dev)<br/>검증 완료된 기능만 통합"]
    end

    subgraph Tier1["Tier 1: 불변 배포선"]
        Main["main (Production Release 전용)<br/>직접 커밋 차단 + Annotated Tag (v1.0.0, v2.0.0)"]
    end

    Exp -->|"성공 시 Squash Merge 후 브랜치 즉시 삭제"| Dev
    Exp -.->|"실패 시 git branch -D 즉시 폐기"| Discard(["히스토리 오염 없음 (Zero Revert)"])
    Feat -->|"검증 후 병합 및 브랜치 삭제"| Dev
    Dev -->|"배포 확정 시 --no-ff Merge + git tag -a"| Main
계층 브랜치 패턴 핵심 역할 병합 및 수명 주기 규칙
Tier 1 (배포선) main 실제 배포 확정 버전만 보관하는 불변 브랜치 직접 커밋 금지, --no-ff 병합 후 즉시 Annotated Tag(vX.Y.Z) 생성
Tier 2 (통합선) v{Major}.{Minor}-dev 차기 배포 버전의 검증 완료된 기능 통합 미검증 실험 직접 수행 금지, 하위 작업 브랜치의 검증 결과만 수용
Tier 3 (작업/실험선) feat/*, fix/*, exp/* AI 에이전트 단위 작업 및 R&D 샌드박스 격리 성공 시 vX.Y-dev로 Squash Merge 후 즉시 삭제, 실패 시 즉시 폐기

2.1 Tier 1: main (불변 배포선과 Annotated Tag)

main 브랜치는 크롬 웹 스토어 심사 제출이나 릴리즈 바이너리 배포처럼 실제 배포가 확정된 시점에만 갱신되는 브랜치입니다. AI 에이전트나 동기화 스크립트가 main 브랜치 위에서 직접 파일을 수정하거나 커밋하는 것을 원천 차단합니다.

차기 버전 통합 브랜치(예: v2.0-dev)의 개발이 마무리되면 --no-ff(No Fast-Forward) 옵션으로 main에 병합하여 명시적인 릴리즈 병합 커밋을 남깁니다. 병합 직후에는 단순 포인터인 Lightweight 태그 대신, 생성 시각과 릴리즈 메타데이터를 온전히 보존하는 Annotated Git Tag(git tag -a v2.0.0)를 생성하여 버전별 히스토리를 영구적으로 고정합니다.

2.2 Tier 2: v{Major}.{Minor}-dev (버전 통합선 및 핫픽스 대응)

v2.0-dev와 같은 버전 통합 브랜치는 해당 버전에 포함될 기능 중 동작 검증이 끝난 코드만 모이는 기준선입니다. 이전 배포 버전(예: v1.0.0)을 사용 중인 환경에서 긴급한 버그 수정이 필요한 경우에는 v2.0-dev의 미완성 코드가 섞이지 않도록 다음과 같이 처리합니다.

  1. 태그 기반 핫픽스 분기: v1.0.0 태그(또는 main)에서 hotfix/v1.0.1-{이슈명} 브랜치를 생성합니다.
  2. 독립 패치 및 배포: 버그를 수정하고 패키징 검증을 마친 뒤 main 브랜치에 --no-ff로 병합하고 v1.0.1 태그를 부여합니다.
  3. 차기 버전 동기화: 수정된 커밋을 현재 개발 중인 v2.0-dev 브랜치로 git cherry-pick하거나 병합하여 동일한 버그가 차기 버전에서 재발하지 않도록 반영합니다.

2.3 Tier 3: feat/*, fix/*, exp/* (AI 에이전트 작업 및 실험 격리선)

이 전략에서 가장 중요한 계층은 AI 에이전트에게 실제 구현이나 실험을 시킬 때 사용하는 작업 브랜치입니다. 작업 성격에 따라 세 가지 접두사를 구분하여 사용합니다.

  • feat/{기능명}: 요구사항과 설계가 확정된 단일 기능 구현 시 분기합니다.
  • fix/{이슈명}: 원인이 파악된 단일 버그나 예외 처리 수정 시 분기합니다.
  • exp/{실험명}: OCR 모델 교체, 프롬프트 구조 변경, 새로운 렌더링 방식 테스트처럼 실패 가능성이 있는 R&D 및 프로토타이핑을 AI 에이전트에게 지시할 때 필수로 생성하는 샌드박스 브랜치입니다.

3. 실험 브랜치(exp/*)와 Squash Merge 운용 원칙

AI 코딩 에이전트와 함께 R&D를 진행할 때는 한 번에 원하는 결과가 나오기보다 파라미터를 조정하고 중간 상태를 확인하는 수십 번의 반복 커밋이 발생합니다. 이때 exp/* 브랜치와 Squash Merge(압축 병합)를 결합하면 실험의 자유도와 통합 브랜치의 청결도를 동시에 확보할 수 있습니다.

3.1 실험 중에는 자유롭게, 병합은 단 1개의 커밋으로

exp/* 브랜치 내부에서는 에이전트가 체크포인트를 자주 남길 수 있도록 wip, debug, test 성격의 세분화된 커밋을 제한 없이 허용합니다. 이후 실험 결과에 따라 두 가지 경로 중 하나로만 처리합니다.

  • 실험 성공 시 (Squash Merge 후 즉시 삭제): v2.0-dev 브랜치로 전환한 뒤 git merge --squash exp/{실험명}을 실행합니다. 실험 과정에서 발생한 20~30개의 시행착오 커밋이 워킹 트리의 단일 변경사항으로 합쳐지며, 여기에 규격화된 커밋 메시지를 부여해 단 1개의 커밋으로 기록합니다. 병합이 끝나면 공통 조상 불일치로 인한 향후 충돌을 막기 위해 exp/{실험명} 브랜치를 즉시 삭제(git branch -D)합니다.
  • 실험 실패 및 폐기 시 (Zero Revert): 실험 결과가 기대에 미치지 못하거나 다른 에이전트의 접근법이 잘못되었을 때는 통합 브랜치에 revert 커밋을 남기지 않습니다. 단순히 v2.0-dev로 체크아웃하여 복귀한 뒤 git branch -D exp/{실험명} 명령으로 실험 브랜치를 즉시 삭제합니다.

3.2 단계별 표준 Git 명령어 레퍼런스

실제 개발 사이클에서 반복적으로 사용하는 명령어 흐름은 다음과 같습니다.

# 1. 통합 브랜치 최신화 및 AI 실험 브랜치 생성
git checkout v2.0-dev
git pull origin v2.0-dev
git checkout -b exp/hybrid-ocr-pipeline

# (AI 에이전트 작업 및 다수의 중간 커밋 진행...)

# 2-A. 실험 성공 시: v2.0-dev로 Squash Merge 후 실험 브랜치 즉시 삭제
git checkout v2.0-dev
git merge --squash exp/hybrid-ocr-pipeline
git commit -m "feat(ocr): PP-OCRv6 하이브리드 파이프라인 도입 및 크롭 합성 최적화"
git push origin v2.0-dev
git branch -D exp/hybrid-ocr-pipeline

# 2-B. 실험 실패 시: revert 없이 v2.0-dev 복귀 후 실험 브랜치 즉시 삭제
git checkout v2.0-dev
git branch -D exp/hybrid-ocr-pipeline

# 3. 정식 버전 배포 확정 시: main 병합(--no-ff) 및 Annotated Tag 생성
git checkout main
git pull origin main
git merge --no-ff v2.0-dev -m "release: v2.0.0"
git tag -a v2.0.0 -m "Release v2.0.0"
git push origin main
git push origin v2.0.0

4. AGENTS.md 및 git-sync.ps1 동기화 가드레일 개편

브랜치 전략을 문서로만 정의해두면 AI 에이전트가 자동 커밋을 수행할 때 다시 기존 습관대로 통합 브랜치에 직접 커밋하거나 문서와 소스를 섞어버릴 수 있습니다. 이를 방지하기 위해 프로젝트 루트의 에이전트 지침(AGENTS.md)과 동기화 스크립트(scripts/git-sync.ps1)에 네 가지 기술적 가드레일을 적용했습니다.

  1. 강제 브랜치 전환 로직 제거: manifest.json이나 package.json의 버전 문자열을 파싱해 브랜치를 임의로 바꾸는 코드를 제거하고, 현재 체크아웃된 작업 브랜치(git branch --show-current)를 그대로 유지하도록 변경했습니다.
  2. main 브랜치 직접 커밋 차단 (Hard Guard): 현재 활성화된 브랜치가 main이거나 Detached HEAD 상태일 때 동기화 스크립트가 호출되면 즉시 오류를 출력하고 종료(exit 1)합니다.
  3. 문서와 코드 변경사항 혼합 스테이징 금지: docs: 커밋에 src/ 코드나 설정 파일이 함께 들어가지 않도록 커밋 전 git status --short 출력과 논리적 단위 분리를 의무화했습니다.
  4. 패키징 무결성 선행 검증: 커밋 전 빌드 및 패키징 스크립트(node scripts/package.js)를 먼저 실행하여 구문 오류나 누락 파일이 발견되면 커밋을 중단합니다.
# 개편된 표준 scripts/git-sync.ps1 템플릿
param (
    [Parameter(Mandatory = $true)]
    [string]$Message
)

$ErrorActionPreference = "Stop"

# 1. NextCloud 동기화 index.lock 해제 대기
$lockFile = Join-Path $PSScriptRoot "..\.git\index.lock"
if (Test-Path $lockFile) {
    Start-Sleep -Seconds 1
    if (Test-Path $lockFile) { Remove-Item -Force $lockFile }
}

# 2. 현재 브랜치 확인 및 main 직접 커밋 차단 (Hard Guard)
$currentBranch = (git branch --show-current).Trim()
if (-not $currentBranch) {
    Write-Error "[Guard] Detached HEAD 상태에서는 동기화할 수 없습니다."
    exit 1
}
if ($currentBranch -eq "main") {
    Write-Error "[Guard] 'main' 브랜치에는 직접 커밋할 수 없습니다. 'vX.Y-dev', 'feat/*', 'fix/*', 'exp/*' 브랜치로 전환하세요."
    exit 1
}

Write-Host "[Git Sync] 현재 작업 브랜치: $currentBranch" -ForegroundColor Cyan

# 3. 패키징/빌드 무결성 선행 검증
if (Test-Path (Join-Path $PSScriptRoot "package.js")) {
    node (Join-Path $PSScriptRoot "package.js")
    if ($LASTEXITCODE -ne 0) {
        Write-Error "[Error] 패키징 검증 실패로 커밋을 중단합니다."
        exit 1
    }
}

# 4. 변경사항 확인 및 목록 출력
$status = git status --porcelain
if (-not $status) {
    Write-Host "[Git Sync] 커밋할 변경사항이 없습니다." -ForegroundColor Green
    exit 0
}

Write-Host "[Git Sync] 스테이징 대상 파일:" -ForegroundColor Yellow
git status --short

# 5. 커밋 및 현재 작업 브랜치 원격 푸시
git add -A
git commit -m $Message
git push origin $currentBranch
