지난 10편에서는 긴 기술 문서와 무한 스크롤 웹페이지에서 발생하던 429 Resource Exhausted 쿼터 제한을 큐 후방 재진입(Re-enqueuing) 지속 루프와 중앙 통합 프롬프트 빌더로 극복하여, 단 한 줄의 누락 없는 100% 완주 번역 파이프라인을 완성했습니다.

쿼터와 프롬프트를 완벽히 통제하고 안정적으로 웹서핑을 즐기던 어느 날, 갑자기 브라우저 내 모든 번역이 한순간에 멈추고 콘솔에 다음과 같은 붉은 에러 로그가 쏟아져 내리기 시작했습니다: 

[WebTranslator] 배치 1 오류 — 스킵하고 계속 진행
Error: 404 This model models/gemini-2.5-flash is no longer available to new users

구글이 실험용 프리뷰 모델을 예고 없이 종료(Deprecated)하거나 이름을 변경하면서, 소스 코드 내에 고정 문자열로 박아두었던 모델명이 404 Not Found로 증발해 버린 것입니다.

이번 글에서는 클라이언트 코드 내 하드코딩의 구조적 취약점을 분석하고, 사용자의 API 키를 바탕으로 현재 계정에서 즉시 사용 가능한 최신 Flash 모델을 실시간으로 감지하고 캐싱하는 동적 모델 탐색(Dynamic Model Fetch) 자가 치유(Self-Healing) 시스템 구축 과정을 다루어 보겠습니다.

1. 모델 하드코딩의 복병: 예고 없는 구글의 모델 지원 중단

클라우드 기반 LLM 생태계는 발전 속도가 매우 빠릅니다. 빅테크 기업들은 새로운 아키텍처를 출시할 때마다 실험용 모델(Preview)을 수시로 교체하거나 레거시 엔드포인트를 폐기합니다.

모델 식별 방식 동작 방식 문제점 및 리스크
정적 하드코딩 코드 내 models/gemini-2.5-flash 문자열 고정 구글 측 모델 정책 변경 시 즉시 404 에러로 서비스 전면 마비
실시간 동적 탐색 GET /v1beta/models 호출 후 최신 모델 자동 선별 별도의 확장 프로그램 업데이트 없이 영구적인 자가 치유(Self-Healing) 보장

당시 개발 코드에는 성능과 가성비가 가장 좋다는 이유로 특정 프리뷰 모델명이 하드코딩되어 있었습니다. 그러나 구글이 해당 프리뷰 모델을 정식 라인업에서 내리자마자 확장 프로그램 전체가 먹통이 되는 치명적인 단일 실패점(SPOF)으로 작용했습니다.

2. AI의 단순 땜질 실수와 또 다른 하드코딩의 함정

AI 어시스턴트에게 404 모델 삭제 오류를 수정하도록 지시했습니다. 

Gemini 404 모델 삭제 오류를 수정해라. 하드코딩된 모델명을 제거하고, 구글 API에서 실시간으로 가용 모델 목록을 조회하여 최신 플래시 모델을 자동으로 선택하도록 개선해라.

지시를 받은 AI는 아래와 같이 단순히 동작 가능한 다른 모델명으로 또다시 하드코딩을 바꿔 치기 하는 임시방편 코드를 작성해왔습니다. 

// gemini.js: 또 다른 하드코딩 땜질 (오류 코드)
const GEMINI_MODEL = "gemini-1.5-flash-latest"; // 임시 땜질! 모델 버전업 시 또 404 발생 위험

왜 이것이 근본적인 해결책이 될 수 없는가?

임시로 모델 이름을 바꿨을 뿐, 몇 주 뒤 구글이 또다시 모델 네이밍 규칙을 바꾸거나 접미사를 폐기하면 동일한 404 Not Found 에러가 재발합니다. 사용자가 확장 프로그램을 매번 수동 업데이트하지 않고도 영구적으로 동작하게 만들려면 실시간 API 메타데이터 조회가 필수적이었습니다.

⚠️ 핵심 결함: 외부 AI 공급자의 모델 수명 주기는 클라이언트 개발자가 제어할 수 없습니다. 따라서 고정 문자열에 의존하는 코드는 시한폭탄과 같습니다.

3. 해결책: 실시간 가용 모델 동적 탐색 (`getValidGeminiModel`)

하드코딩 돌려막기를 전면 금지하고, 사용자의 API Key로 구글 모델 엔드포인트(GET /v1beta/models)를 직접 호출하여 현재 계정에서 실제로 호출 가능한 최신 Flash 모델을 실시간 자동 선별하도록 지시를 수정했습니다. 

하드코딩으로 돌려막지 마라! https://generativelanguage.googleapis.com/v1beta/models?key=${apiKey}를 호출하여 사용자의 계정에서 지원되는 모델 목록 중 generateContent를 지원하는 가장 빠르고 최신의 Flash 모델을 실시간으로 자동 선택하는 알고리즘을 작성해라.
필터링 조건 검사 로직 선별 목적
1. 콘텐츠 생성 지원 supportedGenerationMethods.includes("generateContent") 임베딩 전용 모델이나 비번역 모델 제외
2. 고속 Flash 계열 model.name.includes("flash") 웹페이지 대량 번역에 최적화된 저지연 고속 모델 추출
3. 레거시 모델 배제 !model.name.includes("legacy") 곧 지원 중단될 구형 모델 우선 배제

4. 메모리 캐싱 및 3단계 안전 Fallback 아키텍처

동적 모델 탐색을 매 번역 요청마다 호출하면 불필요한 네트워크 왕복 지연(RTT)이 발생합니다. 이를 방지하기 위해 세션 메모리 캐싱과 네트워크 오류 시 3단계 안전 Fallback을 적용했습니다. 

// src/background/engines/gemini.js: 실시간 가용 모델 동적 탐색 및 캐싱 모듈
let cachedModelName = null;

export async function getValidGeminiModel(apiKey) {
  // 1. 이미 검증된 모델명이 메모리에 캐시되어 있다면 즉시 반환
  if (cachedModelName) {
    return cachedModelName;
  }

  try {
    const response = await fetch(
      `https://generativelanguage.googleapis.com/v1beta/models?key=${apiKey}`
    );
    const data = await response.json();

    if (data.models && Array.isArray(data.models)) {
      // 2. generateContent를 지원하는 flash 계열 최신 모델 필터링
      const flashModel = data.models.find(
        (m) =>
          m.supportedGenerationMethods?.includes("generateContent") &&
          m.name.includes("flash") &&
          !m.name.includes("legacy")
      );

      if (flashModel) {
        // "models/gemini-1.5-flash" -> "gemini-1.5-flash" 정제
        cachedModelName = flashModel.name.replace("models/", "");
        console.log(`[WebTranslator] 최신 가용 Gemini 모델 자동 탐색 성공: ${cachedModelName}`);
        return cachedModelName;
      }
    }
  } catch (err) {
    console.warn("[WebTranslator] 모델 목록 동적 조회 실패, 기본 Fallback 모델을 사용합니다:", err);
  }

  // 3. 네트워크 단절 또는 API 메타데이터 조회 실패 시 최후의 안전 기본값
  return "gemini-1.5-flash";
}

5. 검증 결과: 영구적인 자가 치유(Self-Healing) 달성

  1. 404 에러 영구 박멸: 구글이 특정 모델을 내리거나 신규 버전을 배포하더라도, 확장 프로그램이 첫 실행 시 자동으로 가용한 최신 Flash 모델을 스스로 찾아내어 호출했습니다.
  2. 무중단 브라우징: 사용자가 API 키만 입력해 두면 백그라운드에서 모델 라이프사이클을 스스로 관리하므로, 어떤 외부 정책 변경에도 번역이 중단되지 않는 강력한 내구성을 확보했습니다.

마무리하며

동적 모델 탐색을 통해 모델 Deprecated 사태를 완벽하게 극복했으나, 스팀 커뮤니티나 레딧처럼 특수문자, 이모지, 복잡한 인라인 HTML 태그가 뒤섞인 긴 포럼 글을 번역할 때 간헐적으로 "번역 응답이 비어 있습니다"라는 빈 문자열 응답이 오며 번역이 멈춰버리는 무한 로딩 버그가 나타났습니다.

다음 글에서는 빈 응답(Empty Response) 수신 시 자동으로 원인을 분석하고 재시도하는 Empty Response Retry 메커니즘 구축 과정을 다루어 보겠습니다.
