지난 1편에서는 구글 NotebookLM의 한계를 짚고 Antigravity 에이전트 단독 루프로 전환한 배경을 다루었고, 2편에서는 4대 지시서 체계와 Median UI 하네스, jsDelivr CDN 이미지 동기화 파이프라인의 실전 시행착오를 정리한 바 있습니다.

2편을 작성하고 불과 하루 만에, BlogDocs 자동화 시스템은 또 한 번의 거대한 아키텍처 격변을 겪었습니다. 기존 시스템이 '하나의 레포지토리 안에서 프롬프트 지시서로 에이전트를 조율하던 구조'였다면, 이번 3세대(v3.0) 전환은 Control Plane(지능/규칙)과 Data Plane(콘텐츠/데이터)을 물리적으로 분리하는 분산 아키텍처를 구축하고, Antigravity 2.0 네이티브 Skill & Rule 시스템으로 전면 재편한 것이 핵심입니다.

이번 글에서는 단순한 기능 업데이트를 넘어, 시스템을 운영하며 겪었던 수많은 좌충우돌 사건·사고들과 그 과정에서 단단하게 벼려진 하네스 가드레일, 그리고 완전히 새로워진 v3.0 자동화 워크플로우를 가감 없이 공유하고자 합니다.

1. 왜 단일 레포지토리를 쪼개야 했는가 — Control Plane vs Data Plane

초기 BlogDocs 프로젝트는 단일 Git 레포지토리 안에 모든 것을 담고 있었습니다. 에이전트가 읽어야 할 지시서(Instructions)와 페르소나 설정은 물론, 수집된 기술 지식 베이스(Knowledge), 발행된 HTML 원본, 심지어 CDN 배포용 이미지 파일까지 한곳에 뒤섞여 적재되었습니다.

애초에 BlogDocs를 구상할 때의 본래 목적은 '여러 블로그를 중앙에서 일관되게 관리하고 포스팅을 자동 생산하는 범용 제어 시스템'이었습니다. 그러나 단일 레포지토리 구조에서는 포스팅과 이미지가 쌓일수록 프로젝트 용량이 기하급수적으로 비대해졌고, 새로운 블로그(2호, 3호 블로그)를 추가하려고 해도 기존 Core-Archive 블로그의 데이터와 엉키며 확장이 원천적으로 불가능한 한계에 봉착했습니다.

이를 해결하기 위해 시스템의 책임을 명확히 이원화하는 완전 분산형 아키텍처(Decoupled Architecture)를 도입했습니다.

구분 레포지토리 핵심 역할 및 보관 자산 특징
Control Plane BlogDocs • 에이전트 네이티브 스킬 (.agents/skills/)
• 전역 상시 가드레일 룰 (.agents/rules/)
• 블로그 페르소나 메타 설정 (Instructions/Personas/) 		순수 자동화 엔진 및 컨트롤 타워 (무거운 데이터 일절 배제)
Data Plane Blog_Core-Archive
Blog_NewProject 등 		• 지식 베이스 아카이브 (Knowledge/)
• 발행 HTML 원본 (Blog_Posts/)
• jsDelivr CDN 연동 이미지 (images/)
• 정적 페이지 4종 (Pages/) 		각 블로그별 독립 Git 레포지토리 (데이터 물리적 격리)

에이전트는 Control Plane의 페르소나 파일에 정의된 TargetDir: ../Blog_Core-Archive 속성을 동적으로 참조합니다. 이를 통해 중앙의 에이전트 지능은 가볍게 유지하면서도, 물리적으로 분리된 여러 Data Plane 레포지토리를 자유자재로 넘나들며 지식 수집과 HTML 작성을 수행할 수 있게 되었습니다.

2. 프롬프트 지시서의 종말과 Native Skill & Rule 시스템

2세대 파이프라인의 가장 큰 불안 요소는 '자연어 오발동(False-trigger)'이었습니다. 4개의 긴 지시서 파일(01_Knowledge_Manager.md ~ 04_Static_Pages.md)을 컨텍스트에 상시 주입해두고 @주제, @피드백 같은 텍스트 멘션에 의존하다 보니, 에이전트와 다음 글의 구성을 상의하거나 가벼운 질문을 던지는 일상적인 대화 중에도 에이전트가 이를 명령어로 오인하여 수천 줄의 HTML을 멋대로 쏟아내거나 지식 파일을 덮어써버리는 참사가 빈번했습니다.

v3.0에서는 이러한 프롬프트 기반 지시서를 전면 폐기하고, Antigravity 2.0의 모듈형 Native Skill과 전역 Rule 시스템으로 전면 개편했습니다.

  1. 슬래시 커맨드 기반의 5대 독립 스킬 (.agents/skills/): /1_주제(리서치 및 수집), /2_피드백(실전 검증 및 병합), /3_게시글(HTML 포스팅 및 이미지 생성), /4_발행완료(발행 상태 동기화), /5_블로그추가(새 블로그 인프라 셋업)로 역할을 완벽히 모듈화했습니다. 이제 슬래시(/) 명령어를 명시적으로 호출할 때만 해당 스킬이 격리 실행되므로 자연어 대화 도중의 오발동이 원천 차단되었습니다.
  2. Rules 경량화와 온디맨드(On-demand) 스펙 분리: 상시 규칙(blog-harness-rules.md, trigger: always_on)은 모든 대화에 기본 로드되므로, 기존에 포함되어 있던 방대한 Median UI CSS 클래스 예시와 상세 마크업 스펙을 완전히 제거했습니다. 상시 룰에는 3대 필수 가드레일(경험 우선 글쓰기, 순수 HTML 원칙, De-AI 이미지 규칙)만 간결하게 압축 보존하고, 상세 컴포넌트 마크업 스펙은 실제 글을 생성하는 3_게시글/SKILL.md 내부로 이전하여 모든 대화 세션의 컨텍스트 토큰을 대폭 절감했습니다.
  3. /5_블로그추가를 통한 멀티 블로그 원클릭 확장: 새로운 블로그를 개설할 때 번거로운 초기 세팅을 자동화했습니다. 식별자와 도메인만 입력하면 페르소나 마크다운 생성, 4대 필수 정적 페이지(About, Privacy Policy, Contact, Terms of Service)의 테마 중립적 자동 렌더링, GitHub 레포지토리 초기화까지 원클릭으로 완결됩니다.

3. 디자인과 UI의 진화 — 위젯 통합과 동적 탭 네비게이션

블로그의 시각적 완성도와 UI 측면에서도 중요한 전환점이 있었습니다. 단순히 테마 XML 코드를 수정하는 데 그치지 않고, Blogger 관리자의 '레이아웃(Layout)' GUI 위젯 설정과 Median UI의 동적 컴포넌트들을 유기적으로 결합했습니다.

💡 하이브리드 UI 커스터마이징 주요 내역:
  • 사이드바 계층 메뉴 위젯: 블로그 페르소나에 맞춘 카테고리 트리(게임개발, 홈 서버, AI 도구 등)를 계층형 링크 리스트 위젯과 연동하여 정렬 일관성을 확보했습니다.
  • 상단 공지 슬라이더 위젯 (slider-notice-widget): 홈 화면 최상단에 주요 공지사항이나 최신 기획 연재를 슬라이드 배너 형태로 동적 노출하는 sliderNoticeSec 섹션을 활성화했습니다.
  • Blogger Label 정렬 패치: Blogger 코어가 라벨을 알파벳 순으로 강제 정렬하여 카드 UI의 in {라벨}에 세부 태그가 먼저 노출되던 문제를 테마 렌더링 로직 수정을 통해 메타데이터의 1번째(메인 카테고리) 및 2번째 라벨이 항상 우선 노출되도록 개선했습니다.

특히 가장 큰 기술적 진보는 시리즈 네비게이션 UI의 동적 탭 분리입니다. 기존에는 본문 하단에 '이전 글 / 다음 글' 링크 박스를 HTML로 하드코딩하거나 구상 단계의 메모에 의존했습니다. 이로 인해 시리즈 중간에 새 글이 추가되면 과거 모든 글의 링크를 수작업으로 수정해야 했고, AI가 존재하지도 않는 미래의 글(Next Slug)을 지어내어 링크가 터지는 참사가 발생했습니다.

v3.0에서는 본문 HTML 내 일체의 정적 링크 삽입을 금지하고, 오직 데이터 속성을 가진 컨테이너만 선언하도록 하네스를 확립했습니다.

블로그스팟 테마의 클라이언트 자바스크립트가 Blogger Label 피드를 비동기 조회하여 '📌 시리즈 목록' 탭(이전/다음 글 네비게이션 카드 + 접이식 전체 목차)과 '✨ 관심이 있을 만한 글' 탭을 실시간으로 렌더링합니다. 미래 예측 필드는 시스템에서 영구 추방되었고, 오직 과거 글을 가리키는 Prev Slug만 기록하게 함으로써 링크 정합성을 완벽하게 보장하게 되었습니다.

4. 좌충우돌 비하인드 스토리 — 참사가 낳은 가드레일들

시스템의 모든 가드레일은 평화로운 설계 회의에서 나온 것이 아닙니다. 실제로 파이프라인을 굴리며 마주쳤던 아찔한 사건·사고들을 직접 들이받으며 하나씩 세워 올린 생존의 기록입니다.

⚠️ v3.0 구축 과정에서 겪은 6대 사건·사고와 변화:
  • 사건 1 (자연어 오발동 사건): "다음 편 주제 뭐로 할까?"라는 가벼운 질문에 에이전트가 "네! @게시글 명령어로 인식했습니다"라며 수천 줄의 코드를 쏟아내고 문서를 덮어씀.
    → 변화: 텍스트 멘션 폐기, Antigravity Native Skill 및 슬래시 커맨드(/)로 완전 격리.
  • 사건 2 (상시 룰 토큰 누수 사건): 가드레일을 꼼꼼히 만든답시고 blog-harness-rules.md에 모든 CSS 클래스와 HTML 예시를 적어두었더니, 글쓰기와 무관한 모든 대화에서 매 턴마다 수천 토큰이 낭비되어 컨텍스트 창이 조기 포화됨.
    → 변화: 전역 상시 룰 초경량화(3대 가드레일만 보존) 및 상세 스펙의 3_게시글/SKILL.md 온디맨드 분리.
  • 사건 3 (스킬 네이밍 파편화 사건): 단일 레포의 한계를 절감하고 Data Plane 분리를 추진하며 5_블로그추가를 뒤늦게 신설했으나, 기존 1~4번 스킬과 폴더명/스킬명이 어긋나 슬래시 커맨드 호출 혼선 발생.
    → 변화: 1_주제/부터 5_블로그추가/까지 디렉토리명과 Frontmatter name을 100% 일치시켜 정규화.
  • 사건 4 (미완성 구상과 Next Slug 뇌피셜 대참사): 시리즈 네비게이션이 동작 검증도 안 된 '구상' 메모 상태였는데, AI가 이를 보고 사용자가 허용한 적도 없는 다음 편 링크(Next Slug)를 제멋대로 상상해서 작성함. 전 게시글 404 에러 발생으로 과거 글 전체를 수동 재수정하는 노가다 발생.
    → 변화: 본문 하드코딩 금지, 테마 피드 기반 동적 탭 네비게이션 개발 및 미래 예측 필드 영구 금지.
  • 사건 5 (테마 XML 초기화 참사와 새벽 복구 노가다): Control/Data Plane 레포지토리 분리 작업 중, 유료 테마(Median-UI 1.7.xml)가 public CDN 이미지 배포용 레포의 .gitignore에 들어가 있어 Git 추적이 안 되던 탓에 테마와 위젯 설정이 통째로 날아감. 커밋 롤백이 불가능해 백업본과 기억을 더듬어 새벽 내내 한 줄씩 수동 복구함.
    → 변화: Data Plane에서 커스텀 테마 XML 확실한 버전 관리, /5_블로그추가 내 테마 중립적 정적 페이지 생성 로직 내재화.
  • 사건 6 (인라인 스타일의 다크 모드 파괴): AI가 <img> 태그에 습관적으로 style="width: 100%; border-radius: 8px;"을 넣어 테마 자체의 다크 모드 테두리와 반응형 미디어 쿼리가 파괴됨.
    → 변화: 인라인 style="" 속성 삽입 절대 금지, 테마 글로벌 CSS에 반응형 레이아웃 전적 위임.

5. 아직 남아있는 과제들과 다음 발걸음

v3.0 분산 아키텍처를 통해 상당한 안정성을 확보했지만, 프로덕션 레벨의 완전 자동화를 위해 해결해야 할 과제들도 명확히 정의되어 있습니다.

  1. 유료 Median UI 테마 저작권 보호 및 3-Tier 아키텍처 완성: 현재 유료 라이선스 테마 XML이 public 레포지토리인 Blog_Core-Archive에 노출되어 있는 보안 리스크를 해소하기 위해, 이미지 배포 전용 public 레포(Blog_Images)와 콘텐츠/테마 보관용 private 레포(Data Plane)를 완전히 분리하는 3-Tier 보안 체계를 도입할 예정입니다.
  2. 테마 XML 내부 레거시/하드코딩 요소 대청소: 커스텀 XML 파일 내부에 방치된 구버전 데모용 더미 링크와 미사용 인라인 스크립트를 전면 정리하여 렌더링 속도와 코드 가독성을 끌어올릴 계획입니다.
  3. /5_블로그추가 스킬의 실전 엔드투엔드 필드 테스트: 실제 2호 블로그를 개설하고 페르소나 생성부터 정적 페이지 4종 자동 렌더링, 깃 연동까지 전 과정을 무중단으로 테스트할 예정입니다.
  4. 독립형 모던 댓글 시스템(Waline/Giscus) 재도입 검토: 로그인이 강제되고 댓글 삭제 시 UI가 훼손되는 구글 Blogger 기본 댓글의 한계를 극복하기 위해, 테마 디자인과 유기적으로 호환되는 독립형 댓글 시스템의 재도입을 단계적으로 추진합니다.
