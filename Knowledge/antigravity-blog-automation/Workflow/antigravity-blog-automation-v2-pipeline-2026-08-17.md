#### 🔑 Core Concepts (핵심 개념)

* **[1세대(v1, 2026-06)에서 2세대(v2, 2026-08)로의 전환 — 무엇이 바뀌었나]:**
  * 1세대 파이프라인의 핵심 과제는 "NotebookLM 대신 Antigravity 단독 에이전트를 쓰자"는 도구 선택의 문제였다. 리서치→추출→HTML 생성이라는 단순 3단계 텍스트 변환 파이프라인이 전부였고, 실제 발행 포스팅은 3편(2026-06)에 불과했다.
  * 2세대(2026-08)에서는 지시서 체계가 4개 파일(`01`~`04`)로 세분화되었다. 포스팅 편수는 12편 이상으로 늘었으나, 이는 자동화가 심화된 결과라기보다는 쓸 만한 주제(WebTranslator 개발 시리즈 등)가 생기면서 자연스럽게 증가한 것에 가깝다. 본질적인 변화는 **하네스와 지시서 체계가 정비되면서 각 명령이 일관되게 동작하게 된 것**이다. [FACT/OPINION]

* **[4대 @멘션 명령어 체계 — 분기 설계와 현재 한계]:**
  * 1세대에서는 "블로그 HTML 작성해줘" 식의 자연어 요청에 의존했다. 에이전트가 어떤 지시서를 따를지 매번 추론해야 했고, 지시가 섞이거나 누락되는 경우가 잦았다.
  * 2세대에서는 `@주제`(리서치), `@피드백`(검증), `@게시글`(HTML 생성), `@발행완료`(상태 동기화) 4개의 멘션 트리거로 에이전트의 역할을 분기한다. 일정 수준의 안정성은 확보되었으나 아직 가다듬을 여지가 있다. [FACT]
  * **현재 한계:** 실제 사용에서는 `@피드백`, `@게시글` 보다 자연어로 더 많이 입력하고 있는데, 일반적인 질문이나 대화임에도 에이전트가 피드백이나 게시글 생성으로 오해하여 지식 베이스를 수정하거나 HTML을 생성해버리는 오발동이 종종 발생한다. [FACT/USER VERIFIED]
  * **개선 방향:** 패턴이 고정된 작업(메인 이미지 생성 등)은 별도의 멘션 명령어로 정의하고, 해당 명령어를 사용하지 않으면 동작하지 않도록 막는 것이 필요하다. 다만 명령어가 늘어날수록 사용자가 명령어를 잊어버릴 가능성이 있어 이에 대한 안내 체계도 함께 설계해야 한다. [OPINION]

* **[Harness(하네스)와 Guardrail(가드레일) — 바이브 코딩 환경의 생존 전략과 구조적 불안]:**
  * 코딩 전문 지식 없이 AI와 대화하며 결과물을 만드는 바이브 코딩 환경에서는, AI에게 자유도를 주면 반드시 이탈이 발생한다. Gemini 3.7 Flash의 주요 결함 사례는 단순히 하네스가 없어서가 아니라, **하네스를 읽고도 무시하는** 동작에서 비롯된 경우가 더 컸다.
  * `03_Blog_Harness.md` (v2.3)에는 수십 개의 금지 규칙이 명문화되어 있다. 하네스의 모든 규칙은 동등하게 반드시 지켜져야 하는 것들이며, 우선순위를 매기는 것은 적절하지 않다. [FACT]
  * **구조적 불안 및 현황 점검:** 하네스 파일의 분량이 길어질수록 AI 모델의 컨텍스트 창 제한으로 인해 일부 규칙이 제대로 처리되지 않을 가능성이 있다. 2026-08-17 기준 `03_Blog_Harness.md`는 **27.9 KB / 540줄**이며, 한영 혼합 문서 특성상 약 **3,800~5,700 토큰**으로 추산된다. 4개 Instructions 파일 합산은 약 **7,700~11,600 토큰**이다. 모델별 컨텍스트 창 스펙 및 하네스 단일 파일 점유율을 비교하면 다음과 같다.

| 모델 | 컨텍스트 창 | 출력 한도 | 하네스 단일 파일 점유율 |
|------|------|------|------|
| **Gemini 3.7 Flash** | **1,048,576 토큰(1M)** | **64,000 토큰** | 약 **0.5%** |
| **Claude Sonnet 4.6** (`claude-sonnet-4-6`, 2026-02-17 이후) | **1,048,576 토큰(1M)** 네이티브, 별도 조건 없음 | **64,000 토큰** (Batch API 시 300K) | 약 **0.5%** |

  * **Sonnet 4.6의 1M 컨텍스트 특이사항:** 별도 조건 없이 모든 API 사용자에게 기본 제공된다. 장기과과금 추가 요금 없음. Anthropic API, Amazon Bedrock, Google Cloud Vertex AI 모두 지원. 이전 모델(4.5)에서 필요했던 `anthropic-beta: context-1m-2025-08-07` 헤더는 불필요 (obsolete). [FACT]
  * 파일 자체의 토큰 점유율은 사용 모델(Sonnet 4.6, Gemini 3.7 Flash 모두) 미미한 수준이다. 문제는 **대화 히스토리가 쌓이면서 실질 가용 컨텍스트가 줄어드는 것**으로, 장시간 세션에서는 초반에 로드한 규칙이 후반부에서 약해지는 경향이 있다. 이탈이 발생할 때마다 하네스를 보강하며 대응하는 방식으로 운영을 지속한다. [FACT/OPINION]

* **[Median UI v1.7.0 네이티브 통합 — 테마 정착 이후의 일관성 확보]:**
  * 인라인 스타일 문제는 1세대에서 Median UI 테마를 제대로 활용하지 않고 있었기 때문에 발생했다. 2세대 직전 테마 커스터마이징이 본격적으로 완성되었고, 이를 기점으로 하네스에도 테마 네이티브 클래스 사용을 명문화했다.
  * 현재 `.note`, `.note.wr`, `ol.step`, `div.pre.custom`, `div.table.w100.withBg`, `ul.pros`, `ul.cons` 등 네이티브 CSS 클래스를 전면 활용하며, AI가 임의로 인라인 `style=""` 을 삽입하지 못하도록 하네스에서 금지하고 있다. 테마가 거의 완성된 현재 시점에서는 다크 모드 파괴 문제가 크게 줄었다. [FACT]

* **[GitHub + jsDelivr CDN 자동 연동 — 이미지 상태 동기화 문제의 해결]:**
  * 가장 큰 불편은 이미지 처리 방식의 불일치에서 왔다. 1세대에서는 블로그스팟 에디터에 이미지를 수동으로 업로드했는데, 이 과정에서 Antigravity 내부(로컬)의 HTML 상태와 실제 블로그 게시글의 상태가 달라지는 문제가 발생했다. 에디터에서 이미지를 삽입하면 블로그스팟이 자체 서버로 이미지를 리호스팅하며 URL을 임의로 교체해버리기 때문이다.
  * 2세대에서는 GitHub 레포지토리에 이미지를 저장하고, jsDelivr CDN URL을 HTML에 직접 삽입하는 방식으로 전환했다. 이로써 로컬 HTML 파일과 실제 발행된 게시글의 이미지 상태가 항상 동일하게 유지된다. 이 규칙을 정립하고 가장 먼저 한 작업은, 이전에 발행된 모든 게시글의 이미지를 Antigravity 내부 저장 이미지와 동일한 URL로 일괄 업데이트하는 것이었다. [FACT/USER VERIFIED]
  * **BlogDocs 프로젝트의 본래 설계 목적과 현재 상태:** BlogDocs는 원래 **여러 블로그를 관리하고 게시글을 자동 생성하는 범용 툴**로 설계되었다. 지식 베이스 관리도 동일 시스템 내에서 처리한다. 그러나 현재는 Core-Archive 블로그 전용 툴로 운용되고 있는 상태다. [FACT]
  * **향후 계획:** ① 각 블로그별로 별도의 **공개 GitHub 레포지토리**를 생성하여 이미지를 블로그 단위로 분리 관리한다. ② 현재의 `noogyung/BlogDocs` 레포지토리는 **비공개(Private)로 전환**하여 지시서·지식 베이스·드래프트 등 내부 시스템만 관리한다. ③ 장기적으로는 여러 블로그를 관리할 수 있는 **범용 툴로 발전**시켜나간다. [OPINION]

* **[2중 사용자 승인 게이트(Gate 1 / Gate 2) — 현재 실제 동작과의 차이]:**
  * Gate 1(SEO 메타데이터 확인): 비교적 잘 지켜지고 있으며, 제목·라벨·설명이 안정적으로 생성되고 있다. 블로그 사이드바 메뉴 구조에 따른 라벨 분류도 적절히 작동한다.
  * Gate 2(이미지 프롬프트 확인): 실제로는 잘 지켜지지 않고 있다. 다만 현재는 표준 프롬프트 템플릿(3D 레이어 아키텍처 뷰, 듀얼 대시보드 뷰)이 하네스에 고정되어 있어 이미지 자체가 심각하게 문제가 되는 경우는 드물다.
  * **개선 방향:** 메인 이미지 생성은 게시글 작성과 별도의 고정된 작업 흐름으로 분리하고, 명령어 기반으로 트리거하는 방식이 더 적합할 것으로 보인다. 본문 내 보조 이미지는 현재 거의 삽입되지 않고 있으며, 이미지가 필요한 시점을 에이전트가 적극적으로 추천하도록 강화가 필요하다. [OPINION]

#### 🛠️ Procedures (현재 실전 워크플로우 — 4단계 및 각 단계의 개선 과제)

```
[전체 파이프라인 흐름]

@주제 {주제명}          → 01_Knowledge_Manager.md
        ↓
@피드백 {토픽}: {결과}   → 02_Feedback_Manager.md   ← 자연어 오발동 주의
        ↓
@게시글 {토픽명}         → 03_Blog_Harness.md
  └─ Gate 1: SEO 확인   (사용자 승인 대기)
  └─ HTML 작성 + 저장
  └─ 이미지 처리 (메인 이미지 자동 생성 강화 필요)
  └─ Git push + CDN purge 자동 실행
        ↓
@발행완료 {slug}         → 03_Blog_Harness.md
  └─ blog_published: true 갱신
  └─ Git push 자동 실행
```

1. **[1단계: `@주제 {주제명}` — 지식 수집 및 패키지화]** [★★★★★]
   - `01_Knowledge_Manager.md` (v2.1) 발동.
   - 공식 문서 우선(★★★★★) → 전문 미디어(★★★★☆) → 커뮤니티(★★☆☆☆) 순으로 3~7개 출처 리서치.
   - 수집된 정보를 [FACT], [OPINION], [CONFLICT]로 태깅하여 `Knowledge/{Topic}/{Category}/{파일명}.md` 에 저장.
   - 최초 저장 상태는 **반드시 `Experimental`** (예외 없음).
   - `Knowledge/_index.md` 인덱스 자동 갱신 후 즉시 `git push`.
   - **개선 과제:** Knowledge 파일 최초 생성 후 바로 게시글이 생성되는 오동작이 종종 발생한다. 또한 저장 완료 시 "어떤 항목을 직접 확인해야 하는지" 안내 메시지가 제대로 출력되지 않고 있어, 사용자가 검증 포인트를 직접 파악해야 하는 불편이 있다. AI 모델 업데이트 이후로 이 안내가 생략되는 경향이 생겼다. [USER VERIFIED]

2. **[2단계: `@피드백 {토픽}: {경험}` — 실전 검증 및 상태 승격]** [★★★☆☆]
   - `02_Feedback_Manager.md` (v1.3) 발동.
   - 사용자가 실제 설치/테스트를 마친 뒤 성공 여부, 에러 해결 내용, 추가 팁을 입력.
   - PASS → `status: Verified`, PARTIAL → `status: Verified (Partial)`, FAIL → `Experimental` 유지(피드백만 누적).
   - **현재 실태:** 실제로 `@피드백` 멘션을 명시적으로 쓰는 경우보다 자연어로 경험을 전달하는 경우가 더 많다. 이때 에이전트가 일반 대화나 질문을 피드백으로 오해하여 지식 베이스 파일을 수정해버리는 문제가 종종 발생한다. [FACT/USER VERIFIED]
   - **패턴 발견:** 현재 작성하는 글의 대부분은 이미 겪은 경험을 정리하는 형태다. 지식 베이스 작성 → 피드백 → 게시글 순서보다, 게시글을 작성하는 과정에서 지식 베이스의 오류나 누락이 뒤늦게 발견되는 경우가 더 많다. 따라서 지식 베이스와 게시글은 항상 유기적으로 연결되어야 하며, 게시글 수정이 지식 베이스 수정으로 이어지거나 반대의 경우도 서로 반영되어야 한다. [OPINION/USER VERIFIED]

3. **[3단계: `@게시글 {토픽명}` — HTML 포스팅 생성]** [★★★★☆]
   - `03_Blog_Harness.md` (v2.3) 발동. Verified 상태 파일만 소스로 허용.
   - **Gate 1 (필수):** SEO 분석 결과 출력 → 사용자 승인 후에만 HTML 작성 시작. 현재 비교적 안정적으로 동작 중.
   - Median UI v1.7.0 네이티브 클래스 전면 적용(인라인 `style=""` 절대 금지).
   - `Blog_Posts/{blog-id}/{YYYY-MM}/{slug}.html` 로컬 저장 + Knowledge 파일 YAML 갱신(`blog_draft_path`, `blog_draft_date`).
   - **이미지 처리 개선 과제 (중요):**
     * 메인 이미지(슬롯 1)는 지식 베이스 내용을 토대로 게시글 생성과 동시에 자동 생성되도록 변경이 필요하다. 현재는 선택 단계에서 진행되어 흐름이 끊기는 경우가 있다.
     * 본문 보조 이미지(슬롯 2, 3)는 현재 거의 삽입되지 않고 있으며, 이미지를 필요로 하는 위치에서도 추천 자체가 이루어지지 않는 문제가 있다.
     * 메인 이미지 이후의 보조 이미지에 대해서는 사용자에게 선택권을 주는 방식으로 운영하는 게 적절하다.
   - jsDelivr CDN URL 자동 삽입, `git push` + CDN purge 자동 실행.
   - 완료 보고에 블로그스팟 입력란 복사용(제목/라벨/설명) 제공.
   - **라벨 정렬 이슈:** 블로그가 라벨을 생성 순서가 아닌 이름 순(알파벳/가나다)으로 사이드바에 정렬하는 문제가 있다. 해결 가능 여부 미확인. [USER VERIFIED/OPEN]

4. **[4단계: `@발행완료 {slug}` — 발행 상태 동기화 및 마감]** [★★★★★]
   - 사용자가 블로그스팟에 HTML을 붙여넣고 실제 발행한 뒤 명령 입력.
   - Knowledge 파일 `blog_published: true`, `last_modified` 갱신.
   - 구조화된 커밋 메시지(`feat(publish): publish {slug} ...`)로 `git push`.
   - 새로 추가/교체된 이미지 있으면 CDN purge 자동 실행.
   - **미해결 과제:** 이미 발행된 게시글을 나중에 수정하는 경우의 처리 방식이 정의되어 있지 않다. 지식 베이스 수정 없이 HTML만 수정하는 경우와, 지식 베이스가 변경되어 게시글 전체를 재생성하는 경우를 구분하는 기준과 절차가 필요하다. 게시글만 수정할 때 이를 어떻게 기록하고 관리할지도 고민이 필요하다. (2세대 진입 시 테마 정비로 과거 모든 게시글 스타일을 일괄 수정한 경험에서 비롯된 문제의식) [OPEN]
